# Anchor 日志设计基线

- 基线日期：2026-10-11；UI 预览更新：2026-10-12。
- 状态：设计定稿，已实现明确标注的虚拟数据 UI 预览；日志存储、管理接口、CLI 与真实桌面日志接入尚未实现，本轮未打包或发布安装包。
- 定位：**面向本机排障的结构化日志工作台：看清一次请求经过了什么、失败在哪一层，以及已有证据能解释到什么程度。**
- 页面与工程约束沿用[前端设计](frontend.md)；实例、鉴权与生命周期沿用[桌面运行契约](desktop-runtime.md)。本文确定业务语义、首版范围和默认值，不替代实现时的 DTO、迁移与契约验收。

## 1. 产品基调

日志首页围绕请求排障组织，以请求表格和详情面板为主。一次正常调用留下简洁摘要，失败时可以逐层展开；系统事件用于解释启动、连接、持久化与崩溃问题。请求详情必须能回答：

1. 是代理调用还是用户主动推理测试？属于哪个实例、绑定和公开模型？
2. 实际调用了哪个供应商、哪个 Key 标识、哪个上游模型，使用了什么协议及配置版本？
3. 上游返回了什么 HTTP 状态？Anchor 校验或转换是否通过？客户端实际收到了什么？
4. 有几次尝试？为什么重试或切换？是否已经输出过流式内容？
5. 耗时和用量有哪些可靠数据？哪些未知？有没有记录丢失？

默认开启无正文的请求元数据记录和 `info` 级系统日志。默认不保存对话、提示词、工具参数或原始请求响应，不做自动重放；排障动作不能自行产生一次付费模型请求。首版提供安全诊断复制和导出，不提供任意正文全文搜索。

## 3. 当前实现与首版边界

2026-10-12 UI 预览位于 `desktop/frontend/src/features/logs/`，由 Model、hook Controller、View 和合成样例组成，沿用 sidebar-07 / neutral。侧栏“日志”可打开请求与系统两个页签；支持搜索与筛选、请求详情、尝试时间线、安全摘要复制、虚拟 JSON 导出、保留设置预览和新记录提示。所有状态均在内存中，刷新重置，不调用核心日志接口。桌面模式也只展示这个独立且明确标注的设计预览，不是连接失败后的 Mock 回退。

样例覆盖 HTTP 200 校验失败、429 后切换成功、流式中断、推理输出上限、取消、路由失败与核心中断，并可切换记录缺口、空数据和离线状态。缺失响应 ID 是用于展示 `invalid_response` 诊断方式的合成情境，不能据此认定用户真实请求的故障原因。浏览器已验证筛选、关联、导出、详情焦点、浅色/深色与窄窗口；真实存储、容量限制、日志订阅、实例隔离和原生双平台窗口仍需后续实现与验收。

| 当前可核对事实 | 首版需要补齐 |
| --- | --- |
| `internal/core/gateway.go` 为上游尝试写入 `model request`，含模型、供应商、Key、协议、HTTP 状态、成功标记和耗时 | 稳定的根请求、尝试编号、失败阶段、客户端交付情况与可查询历史 |
| `internal/core/provider_workspace.go` 的推理测试返回 Probe，并累计用量 | 推理测试也产生独立请求记录，关联 Probe 和当时的 revision |
| `internal/cli/cli.go` 的 `serve` 使用 JSON slog 输出 stderr | 核心自主写入受限持久日志，终端输出保持单独渠道 |
| `internal/desktop/launch.go` 将后台核心 stdout/stderr 接到空设备 | 日志写入由核心生命周期负责，关闭窗口后继续记录；不能依赖窗口持有管道 |
| `internal/state/provider_features.go` 在 `state.db` 的 `usage_totals` 中累积统计 | 用量汇总继续独立保存；清理请求日志不删除或重新计算累计用量 |
| 侧栏“日志”已开放虚拟数据设计预览，支持表格、详情与系统关联 | 接通真实存储与类型化接口后替换为真实日志工作台，并保持离线、未知与记录缺口语义 |

日志分为三类：

- **请求日志（首版）**：代理推理与主动推理测试，一条根请求下挂多次尝试。失败发生在路由或鉴权前，也可以有零次上游尝试。
- **系统日志（首版）**：核心与宿主的启动、退出、连接、存储故障、日志丢失及关联错误。只记录稳定事件与安全元数据。
- **管理操作审计（后续）**：供应商、Key、绑定、恢复和更新等动作的操作者来源、目标、版本与结果。它与托管恢复 journal 职责不同；不能替代恢复依据，也不能宣称首版覆盖完整审计。

模型目录查询等管理请求首版仅记录必要系统事件，不加入推理请求统计。临时诊断会话、正文捕获、跨进程完整链路、趋势图与统计报表留到后续评估，首版不预留可直接开启的“记录全部正文”开关。

## 4. 一次请求与多次尝试

核心在入口生成不含业务内容的 `request_id`，不直接以外部传入 ID 作为主键。每次尝试以 `(request_id, attempt_no)` 关联；系统事件可携带同一个 ID。实例有稳定 `instance_id`，每次核心启动有新的 `run_id`；系统事件另有进程与来源标识。

历史保存当时的安全配置快照：供应商 ID/名称、Key ID/标签、公开模型、实际模型、供应商/模型配置 revision、协议选择来源（Key 默认或模型覆盖）。只引用 Key 标识，不保存密钥本体、前后缀或密钥摘要。改名、删除、重新配置后，历史仍展示当时的值；当前对象不存在时显示“已删除”，不能把今天的配置拼回旧日志。

| 层级 | 首版字段与语义 |
| --- | --- |
| 根请求 | schema_version、instance/run/request ID、单调序号、创建/结束 UTC 时间、记录 revision、来源 `proxy/probe`、可确认的 binding ID、公开模型、入口协议、stream、最终状态、总耗时、尝试次数、最终尝试编号、失败阶段/代码、交付状态 |
| 上游尝试 | attempt_no、供应商/Key/实际模型及版本快照、上下游协议与转换路径、开始/结束时间、耗时、首字节耗时（可测时）、HTTP 状态、结构校验结果、错误、重试决策、用量 |
| 结构诊断 | 预期格式、实际媒体类型分类、已读字节数、响应 ID 是否存在、已识别的 output/event 类型集合、未知类型数、响应生成状态、固定 incomplete 原因、请求输出上限 |
| 系统事件 | schema_version、event_id、UTC 时间、level、source、稳定 event、固定 message、instance/run/process ID；可选 request ID、阶段、耗时、允许的上下文字段和错误代码 |

使用 UTC 存储，界面按本地时区展示并在详情标出时区；耗时用单调时钟测量。首字节耗时不称为首 Token 耗时；未获得的时间、字节、状态及用量为 `null`，不能补零。流式首 Token 指标只有能可靠识别 Token 边界后才增加。

上游 request ID 仅接受已知头中的长度/字符校验与脱敏后的标识；不存整份响应头，也不假定这个 ID 永远存在。客户端关联 ID 与核心 ID 分字段，未确认绑定时不由 User-Agent 推断具体 Agent 身份。

### 4.1 结果必须分层

| 维度 | 表达 |
| --- | --- |
| 上游传输 | `http_status` 或网络错误；未发送为 null |
| Anchor 处理 | `validation/transform` 结果及固定错误代码；HTTP 200 不能代替这层判断 |
| 生成结果 | `completed / incomplete / failed / unknown` 与允许的原因；与传输结果独立 |
| 客户端交付 | `none / partial / complete / unknown`，可有已提交的 downstream HTTP 状态；主机写出完成不证明客户端应用已消费 |
| 根请求状态 | `pending / succeeded / failed / cancelled / interrupted`；最后一次尝试的失败不覆盖此前已交付内容 |

重试成功的根请求显示“成功 · 2 次尝试”，详情保留第一次失败；统计一条请求、两次上游尝试。各尝试用量分别展示，包括失败尝试已知的消耗；根请求只有所有计入项均已知时才显示完整总用量，否则显示“已知小计，部分未知”。价格估算继续引用既有用量/价格规则，首版不另造计费逻辑。

流式已输出后再断连，显示“失败 · 已输出部分内容”，记录输出阶段和取消来源；不让日志触发供应商重放。客户端主动取消与上游故障分开；不能确定取消原因时标记未知。日志不改变现有重试、健康度、冷却或熔断规则。

`pending` 不因窗口关闭转失败。核心异常退出后，由新 run 核对旧 run 的未结束记录并标为 `interrupted`，解释为“核心中断，最终结果未知”；没有可靠证据时不写成供应商失败。持久化的开始记录与完成记录是两次状态转换，不承诺断电情况下每条请求均完整。

### 4.2 推理测试的特殊语义

推理测试必须同时显示“协议校验结果”和“生成状态”。符合探测契约的 reasoning 输出、或因输出上限导致的合法 incomplete，可显示“协议通过 · 达到输出上限”，不能只因为没有可见正文判 `invalid_response`。真实代理仍遵循自己的转换能力；探测通过不等于所有内容都能跨协议转换。

Probe 摘要与请求日志共用同一次测试的结果，不额外发第二个请求取证；界面从供应商测试结果可跳转同一 `request_id` 的日志。实现需一并扩展 Probe DTO 与共享样例，不在前端凭时间和模型模糊匹配。

## 5. 失败解释与 HTTP 200 场景

失败展示由三部分组成：**发生阶段 + 稳定代码 + 有证据的解释**。阶段建议为 `intake / auth / route / request_transform / upstream / response_validate / response_transform / respond / cleanup`，可跳过或重复；既有公开错误代码尽量保留，新增安全诊断原因不冒充已有协议字段。

| 代码 / 诊断原因（拟定） | 安全解释示例 | 可记录的证据 |
| --- | --- | --- |
| `authentication` | 上游拒绝认证 | HTTP 401/403、Key 标识；无认证值 |
| `rate_limited` | 上游限流 | HTTP 429、已校验的等待秒数；不存原始头 |
| `timeout` | 等待上游超时，是否已执行未知 | 超时阶段、实际耗时、是否已收到字节 |
| `invalid_response / invalid_json` | 响应不能解析为预期 JSON | 已读字节数、解析偏移；无响应片段 |
| `invalid_response / unexpected_media_type` | 响应格式与当前协议不匹配 | 媒体类型分类、预期格式 |
| `invalid_response / missing_required_field` | 响应缺少协议必需字段 | 固定字段名称，例如 ID 存在标记 |
| `unsupported_conversion` | 响应包含当前转换器不能表达的内容 | 已识别类型枚举、转换路径；不存内容 |
| `invalid_response / upstream_failed` | 上游在成功 HTTP 状态中声明生成失败 | 生成状态、允许的上游错误分类；无任意错误正文 |
| `invalid_response / read_limit_exceeded` | 响应超过受控读取上限 | 已读字节数、读取上限 |
| `invalid_response / truncated` | 响应读取中断或缺少协议终止事件 | 读取结束原因、固定终止事件存在标记 |

类型集合只接受核心定义的枚举，未知类型仅记数量或“未知类型”，不能把任意上游字段、错误字符串或 JSON 片段塞进诊断。保留稳定父代码便于兼容，子原因用于解释；证据不足时使用 `unknown`，不能为了让文案好看推断根因。

合成示例（不是用户那次请求的已取证结果）：

```text
推理测试失败 · 2606 ms · Key default · revision 2
上游：HTTP 200
Anchor：response_validate / invalid_response
具体原因：缺少协议必需的响应 ID
证据：已读 824 B；JSON 解析通过；has_response_id=false
客户端：测试结果已返回；未代理生成正文
request_id：<核心生成的关联标识>
```

如果没有获取到上述证据，只显示“上游 HTTP 200，但 Anchor 响应校验未通过；具体结构原因未记录”。旧版本只有 `invalid_response` 的记录不得回填猜测。合法 reasoning / token 上限结果则按 §4.2 呈现通过或受限状态。

## 6. 存储、保留与性能预算

请求记录使用核心独占管理的独立 SQLite：`<data-dir>/logs/requests.db`，包括 requests 与 attempts，隔离配置库 `state.db`。系统事件使用轮转 JSONL；核心与宿主分别写自己的文件，避免跨进程争用同一文件。核心文件写入不依赖 GUI 的 stdout/stderr 捕获；启动早期错误由宿主安全提示并写入宿主系统日志。

| 项目 | 首版默认值 / 约束 |
| --- | --- |
| 请求明细保留 | 7 天；默认同时最多 50,000 条根请求，连同其尝试整体清理，任一条件先到即清理最旧记录 |
| 请求存储空间 | DB + WAL + SHM 目标 256 MiB；实际占用达到 320 MiB 时暂停新持久记录并尝试受限回收，恢复到目标内再写入；明确显示缺口 |
| 系统日志 | 核心与宿主各保留 7 天、各最多 16 MiB；单文件约 4 MiB 轮转，按时间/容量先到清理；总预算 32 MiB |
| 单条大小 | 根摘要、尝试、系统事件各最多 8 KiB；字符串最多 256 字符，嵌套最多 4 层；固定枚举与关联 ID 优先保留 |
| 尝试详情上限 | 每个根请求保留最多 16 个尝试详情，超出保留首 8 / 末 8 及 omitted 数；总次数始终准确，不反向限制真实路由 |
| 写入队列 | 至多 1,024 个事件且合计不超过 8 MiB，任一先到；单写入 worker，批次最多 100 条或等待 250 ms |
| 查询与页面 | 默认每页 50，最多 200；查询时间窗最多 30 天；详情限制尝试数与事件大小 |
| 刷新 / 跟随 | 首版有界轮询，活动页面/CLI follow 默认 2 秒；隐藏页面暂停，取消或切换实例即释放 |
| 前端缓存 | 最多 1,000 行摘要，详情按需读取；不缓存原始 JSONL 文件 |

这些是实现目标，容量验收须测量真实文件占用。256 MiB 是回收目标，不是 SQLite 物理硬配额；删除行不代表立即缩小 DB，WAL、checkpoint、空闲页与临时文件均须计入观测。优先复用空闲页和增量回收，首版禁止在服务过程中无预算地执行全库复制式 VACUUM；清理批次不超过 500 个根请求，达到容量阈值时可连续分批清理。异常占用不得用删除配置库或用量表解决。

首次配置保留天数可调整为 1–30 天，条数可调至 1,000–50,000，容量目标可调为 32–256 MiB；容量暂停阈值随目标按 1.25 倍计算。系统日志预算首版固定，避免配置面过大；不提供无限保留。降低预算先返回预计清理范围，确认后按新限制回收；清空支持明确时间范围并连带删除尝试。读日志、导出和清空都不接触累计用量、Key 健康度、配置或恢复 journal。

日志失败不能阻塞模型转发：队列满先丢弃 debug 系统细节，仍不足时允许丢记录，但暴露 `dropped_count / write_error_count / last_write_error_code / degraded_since`。终态优先于过程细节；日志事件限流、合并重复错误，避免日志故障再次制造无限日志。进程内缺口计数不承诺崩溃后完整，下一次启动显示恢复后的完整性状态。发生磁盘满或写入失败时，页面明确“日志记录不完整”，不能展示“没有请求”。

用量继续走既有累计机制，不能因请求日志暂停而停止用量更新，也不能从保留 7 天的明细重建长期汇总。被截断的诊断字段带截断标识；已缓存列表中的请求被清理时返回“已过保留期/已清理”。核心维护有界清理范围水位与最近 1,000 个 ID 的短期墓碑；范围外的任意 ID 只返回“记录不存在或已清理”，不假装能永久区分从未存在与已删除。实例错误、核心离线仍用独立状态表达。

## 7. 隐私与访问边界

先用字段允许列表生成记录，再做字符串脱敏；两者在落盘、管理 API、IPC、复制和导出之前统一执行。日志库不接收任意对象、整份 `Error`、`http.Request` 或响应对象。系统错误采用固定消息、稳定错误码和已批准字段，首版不记录任意堆栈或原始 `err.Error()`。

禁止字段包括：Authorization/Cookie、供应商密钥、管理/绑定令牌、提示词和对话、reasoning 内容、工具参数/结果、上传文件内容、完整请求响应、任意上游错误正文、带凭据或查询参数的 URL。默认不记录 IP、完整 User-Agent、用户绝对配置路径。模型与标签等允许字段也须限长、过滤控制字符并屏蔽已知凭据；认证失败时不能把未经校验的请求字段当成安全标识。

本机目录使用仅当前用户可访问的权限，Linux 文件目标 0600/目录 0700，Windows 对应当前用户 ACL；日志不能另开匿名 HTTP 静态下载入口。管理查询沿用实例 owner 身份、Origin 防护与既有安全边界；绑定数据面令牌无权读取任何日志。前端看不到管理令牌，切换实例隔离列表、详情与异步结果。

安全摘要仍可能包含模型名、供应商名和时间等工作信息。复制/导出由用户主动执行，导出前可预览范围与字段；无默认公开上传、自动遥测或自动发送第三方。导出在受控连接层流式写入用户选择的位置，失败删除任务自有临时文件，不将绝对路径加入普通日志；不提供任意服务器文件读取。

## 8. 桌面页面基调

沿用 `sidebar-07`、shadcn neutral、浅色/深色主题和现有顶栏。日志页使用“请求 / 系统”两个页签，默认请求；管理审计暂不显示可用入口。首屏不放统计大屏或正文瀑布流。2026-10-12 请求表格已支持[27 项可选显示内容](log-columns.md)：按类别勾选、调整顺序、常用/性能/排障预设与恢复默认；只保存本机列偏好，记录仍为虚拟数据。系统表格保持固定字段。

```text
日志 / 请求                           [暂停刷新] [导出] [保留设置]
[最近 1 小时 ▾] [全部结果 ▾] [来源 ▾] [供应商 ▾] [搜索] [显示内容 8]
时间       结果      模型名称     供应商   首字时间   总耗时   TPS    错误码             详情
23:10:18   校验失败  model-a      provider 未知       2606 ms  未知   invalid_response  ›
23:09:42   成功      public-b     provider 584 ms     1834 ms  271.7  —                 ›
                           有 3 条新记录，点击加载

点击一行 → 详情面板：结果解释 → 路由与配置快照 → 尝试时间线 → 用量 → 安全诊断
```

默认时间窗最近 1 小时，可选 15 分钟、24 小时、7 天、自定义；结果筛选含成功、失败、取消、中断、进行中。供应商、Key、模型、来源、HTTP 状态、失败阶段/代码可组合筛选；搜索只针对安全字段，不暗示正文检索。

列表以核心单调序号倒序排列，显示请求开始时间；同一请求更新状态而非新增一行。HTTP 与 Anchor 结果分别标示，根失败时展示终止原因，成功重试时展示尝试数量。用文字/图标配合状态色，模型 ID、关联 ID 使用等宽字体。细节面板可复制 request ID 和安全排障摘要，完整诊断结构折叠展示，缺失数据用“未知”。

滚动查看历史时不自动插入新行或抢焦点；显示新记录数量，用户点击再加载。刷新失败保留上次结果并标出过期状态，区分无记录、无匹配、记录缺口、核心离线、实例不符和保留期失效；详情已清理仍保留可读的列表摘要并提示不可继续读取。窗口关闭、取消、页面卸载和实例切换均取消轮询。

前端按 `features/logs/` 的 Model / hook Controller / View 组织。Model 通过类型化桌面传输访问，Controller 管理筛选、游标、轮询与过期结果隔离，View 负责列表、详情和状态；不直接读 SQLite、日志文件、Wails 绑定或执行 shell。日志配置由核心校验，与界面外观偏好分开。

## 9. CLI 与管理契约计划

以下均为**拟议入口，尚未实现**，不属于[当前指令大全](../cli/commands.md)。实现时优先接通 CLI，再接同一核心能力的 GUI；届时同步帮助、大全、功能覆盖表和真实变更历史。

| 拟议 CLI | 范围 |
| --- | --- |
| `anchor [--context NAME] log list` | 时间/结果/来源/供应商/Key/模型/HTTP/代码过滤与游标分页；支持 JSON 输出 |
| `anchor [--context NAME] log show REQUEST_ID` | 一次请求、各次尝试、安全诊断与数据完整性 |
| `anchor [--context NAME] log follow` | 跟随请求创建及状态更新；取消即结束连接，不只是输出最终成功请求 |
| `anchor [--context NAME] log system` | 有界系统日志查询；来源、level、event、request ID 过滤 |
| `anchor [--context NAME] log export` | 将已筛选安全明细写出 JSONL；带 schema/version、实例、范围与缺口信息 |
| `anchor [--context NAME] log retention` | 读取/修改保留策略，变更携带 expected revision，输出预计删除范围 |
| `anchor [--context NAME] log clear` | 明确时间范围、预览数量与确认后清理；不影响累计用量 |

默认实例/Context 遵循既有规则，不新增另一套连接配置。数据写 stdout，诊断写 stderr，失败使用既有 CLI 错误机制；不要让脚本从中文 message 推断退出码。首版远程跟随仍复用已授权连接，不开放公开日志服务。

核心计划提供类型化的列表、详情、系统列表、状态变更查询、导出、保留配置与清理预览/执行能力。正式路由名和 DTO 在实现轮次定稿；CLI/桌面/Mock 必须共享字段、枚举及合成样例，Go DTO 经生成器产生 TS，禁止手改生成文件。本轮不修改现有共享接口。

查询契约需一次性明确：

- 列表返回 items、next_cursor、实例/run 标识、查询边界与 logging_health；游标绑定实例、筛选条件、schema 和初次查询的最高序号，防止新请求造成重复分页。
- 分页固定成员边界，不承诺冻结请求后续状态；更新使用 record revision。`follow` 使用独立变更序号，区分创建/更新；缓冲失效返回 `resync_required` 并让客户端重查，不能静默漏掉 pending → failed。
- 首版变更环形缓冲最多 1,000 条安全更新或 8 MiB；不持久化无限事件流。服务重启改变 run ID，旧跟随游标要求重新同步。
- 详情与导出同样受 owner 鉴权、实例身份、大小和时间范围约束；单次导出最多 50,000 根请求，流式返回，结束记录是否完整。清理竞态或连接中断不能把半份文件标成完整。
- 保留配置有独立 revision；清理预览与执行绑定实例、范围和配置 revision。过期预览须重新核对，禁止前端绕过核心拼 SQL。
- 核心不可达时请求历史显示离线，不回退 Mock。首版不由宿主直接打开请求 DB；核心启动失败仍应通过已有宿主错误提示和宿主系统文件诊断，离线查看界面另行设计。

## 10. 实施顺序与首版验收

按下面三个可独立核对的里程碑推进；这是后续实施顺序，本轮仅完成设计。

1. **记录链路**：核心 request/attempt 与安全诊断、probe 关联、独立请求库、核心/宿主系统 JSONL、受限队列、保留与缺口状态；先用隔离状态和合成上游验证。
2. **查询与 CLI**：owner 管理接口、游标、请求详情/系统查询/follow、安全导出、保留/清理；完成 CLI 契约与共享 DTO/样例。
3. **桌面日志页**：真实列表、筛选、详情时间线、推理测试跳转、暂停/新记录提示、导出和保留设置；按前端规范验证主题、键盘和实例切换。

首版交付以三步连通为准，不能把“已有日志文件”“Mock 表格”或“测试通过”称为用户可排障。验收至少包括：

| 合成场景 | 必须看见 / 保证 |
| --- | --- |
| HTTP 200 + 缺失协议字段 | 上游 HTTP 200，Anchor 校验失败、具体固定原因与结构证据，无正文 |
| 合法 reasoning-only / 输出上限的 probe | 探测契约通过，生成受限状态清楚；不把无可见文本自动当失败 |
| 第一次 429、第二次成功 | 一根请求两次尝试，等待/切换原因、最终成功；用量已知程度准确 |
| 路由失败且未调用上游 | 零次尝试、route 原因、上游状态为 null |
| 部分流式输出后断开 | 部分交付与断开阶段、无自动重放，取消与故障分开 |
| 删除/改名/修改 Key 协议 | 历史快照保留，当前对象缺失有提示，不泄露 Key |
| 缺失 usage / 日志到期 / 清空日志 | 未知不补零，累计用量仍独立存在 |
| 窗口退出、核心继续运行、异常重启 | 窗口退出不停止日志；旧 pending 恢复为中断且结果未知 |
| 队列满/磁盘满/慢查询 | 转发不等待日志；缺口可见，队列/磁盘/页面内存受限 |
| 恶意响应/错误字符串含秘密 | DB、JSONL、管理 API、IPC、复制、导出均无秘密或对话片段 |
| 错误实例/绑定令牌访问/过期跟随游标 | 身份拒绝；过期显式要求重同步；无 Mock 回退 |
| 翻页同时来新请求、状态随后更新 | 历史不跳行，不丢状态更新；切换实例无旧结果串入 |

验证不改真实 Agent 配置、不调用付费上游。实现时补受影响的单元与合成契约测试；浏览器/宿主等重任务按 resource-guard 串行受限运行，Windows/Linux 原生验收单独报告。写入成本、物理容量、回收和断电耐久性必须用实际测量说明，不把本设计预算写成已测性能。

## 11. 后续能力的边界

管理审计、错误趋势、跨进程关联、受控短时诊断均可在首版稳定后增加。新增字段先说明目的、隐私分类、上限、访问对象和清理方式，再改 DTO 与样例。成本图表沿用用量系统，日志只是证据；首版保留期内的“请求成功率”不能冒充全部历史成功率。

如后续确实需要内容诊断，应另行设计一次性范围、显式授权、短时失效、独立存储/导出和全链路脱敏，不把“开启 debug”解释为允许保存提示词或 reasoning 原文。
