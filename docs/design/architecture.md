## 2. 产品定位

Anchor 是跨平台、无头常驻的本地模型中转与管理工具。

它管理用户选择的现有 Agent 平台，不提供自己的 Agent，不接管推理循环、工具执行或任务编排。其职责是：

1. 为 Agent 提供本地模型 API。
2. 统一供应商配置、模型映射、请求路由与协议转换。
3. 通过可扩展托管层自动配置 Agent 的 API 连接。
4. 支持本机与 SSH 远程管理多个独立实例。

产品形态是中转站，而不是仅在供应商配置之间切换的工具。用户选择托管后，主要平台仍可通过原有命令启动；不要求每次从 Anchor 启动 Agent。

长期产品方向包含 Agent、Skill、API 综合管理，但首版优先模型网关与托管闭环，Skill 管理另列后续范围。

## 3. 已确认需求与范围

| 类别 | 初版要求 |
| --- | --- |
| 平台 | Linux、Windows 必须支持 |
| 无头 | 核心与 CLI 不依赖浏览器、桌面会话或图形凭据交互 |
| 常驻 | 核心代理独立运行，不随管理客户端退出而退出 |
| 当前入口 | 仅 CLI；管理 API 不等于当前开发 Web 页面 |
| 桌面方向 | 后续重点，复用连接组件、类型化 API 和业务能力 |
| 安卓 | 非必需，不阻塞首版；以后可考虑控制端 |
| Agent | 优先 Codex、CC、DSH，并保留非主流平台接入能力 |
| 模型 | 用户配置公开模型和映射；支持在 Agent 的模型选择机制中使用 |
| 协议 | 按客户端需要提供入口，路由到 Responses / Chat / Anthropic 上游 |
| 托管 | 用户显式选择；核心就绪后自动接管，正常停止时条件恢复 |
| 远程 | 通过 SSH 管理另一机器上的 Anchor，不要求配置同步 |
| 可诊断 | 区分配置接管、覆盖冲突和真实请求经过代理的状态 |

以下不在初版范围：

- 自有 Agent 执行引擎、多 Agent 编排、工作流平台。
- 独立 Web 与安卓应用界面；桌面界面不属于当前无头核心 / CLI 里程碑，但已纳入下一阶段的 Windows / Linux 产品目标，见[桌面前端技术设计](frontend.md)。
- Skill 管理、公共插件市场和任意代码插件运行时。
- 多设备配置 / 密钥 / 日志自动同步。
- 默认公网管理入口、系统全局代理、HTTPS 拦截。
- 自动远程安装、提权、修改 SSH 服务或批量管理所有系统用户。
- 复杂负载均衡、跨设备模型流量调度和会话无缝迁移。

## 4. 总体架构

```text
CLI / 未来桌面客户端
          |
          v
Context + Connector + 类型化管理客户端
          |
          v
管理 API / 核心生命周期协调器
          |
          +-- 托管层
          |     +-- 内置适配器：Codex / CC / DSH
          |     +-- 声明式适配器：JSON / YAML / TOML
          |     +-- 绑定、检查、计划与验证
          |
          +-- 统一配置变更与恢复引擎
          |     +-- 路径与字段所有权
          |     +-- 安全备份、恢复日志、冲突处理
          |
          +-- 常驻代理层
                +-- 客户端协议入口与绑定鉴权
                +-- 公开模型与供应商映射
                +-- 路由、超时、并发与容错
                +-- 上游协议转换、流式事件与工具调用
```

这些是职责模块，初版不要求拆成多个服务进程。

### 4.1 模块边界

- 代理层不读取 Agent 配置文件，不识别 TOML / JSON / Cordis 的落盘细节。
- 托管层不负责网络协议转换和供应商调用。
- 适配器生成结构化计划，统一引擎负责备份、应用和撤销。
- CLI 不直接修改远端数据库或拼接远程 Shell 业务命令。
- 托管和恢复发生在 Agent 所在实例；文件路径按目标机器解析。
- 接管字段、凭据和目标范围必须获得用户批准，不能通过导入描述扩大权限。

### 4.2 两条独立链路

```text
管理：控制电脑 CLI -> 本机连接或 SSH 隧道 -> 目标 Anchor 管理 API

模型：目标 Agent -> 同机 Anchor 模型 API -> 上游供应商
```

管理连接关闭不会停止目标核心。控制电脑不进入远端模型链路，也不必运行本机模型代理。

## 5. 代理层

### 5.1 供应商

供应商配置至少包含：名称、Base URL、认证秘密引用、上游协议、模型、启用状态、超时和并发限制。

协议必须明确配置，不能仅按服务商名称猜测。连接测试与模型获取应报告实际结果；不支持模型发现的上游允许手动配置。

供应商密钥保存在目标实例，不写入 Agent 连接配置，也不复制到控制电脑的供应商数据库。

### 5.2 公开模型与模型映射

公开模型是 Agent 面向用户选择的稳定 ID，不等同于上游模型 ID。例如以下名称仅用于说明：

```text
anchor-code
  +-- 主供应商 A -> upstream-code-v1 -> Responses
  +-- 备用供应商 B -> upstream-code-v2 -> Chat Completions
```

模型配置包括公开 ID、显示名称、默认项、能力信息和候选映射。能力至少考虑工具调用、输入内容类型、上下文限制及支持的推理设置；具体字段待实施定稿。

不同实际模型是否作为同一别名的备用项，由用户明确决定，不能静默替换模型语义。

托管适配器将模型信息转换成目标 Agent 的目录或选择配置。Codex 的验收包含在选择器中使用 Anchor 模型，不仅是手动填写名称；不应只提供通用模型列表接口就假定客户端会自动展示。

### 5.3 客户端与上游协议

- 客户端侧：首先完成 Codex 所需的 Responses；CC、DSH 按实际适配器要求增加 / 验证入口。
- 上游侧：设计目标覆盖 Responses、Chat Completions、Anthropic Messages。
- 请求与响应都需转换；不能只改请求 JSON 或包装文本。
- 必须覆盖指令、消息、内容块、工具定义、调用 ID、参数增量、工具结果、完成 / 失败事件及可获得的用量。
- 工具执行仍由 Agent 完成，Anchor 只处理其协议表示。
- 不兼容的能力明确报错；不承诺所有协议可以无损转换。
- 请求取消与下游断开需传播到上游，释放本任务资源。

具体版本、认证头、路径规则、转换字段与测试样本属于实施细节，不由产品名称推断。

### 5.4 初版路由与故障处理

```text
公开模型
 -> 已启用且能力匹配的候选项
 -> 按优先级调用
 -> 在允许的失败条件下尝试备用项
```

没有匹配项时报错，不落到任意默认模型。重试要有界且可诊断；具体重试 / 切换错误矩阵待定稿。请求超时可能存在上游已执行但结果未知的情况，不能宣称重试不会重复计费。

已经向客户端输出流式内容后，不自动切换供应商重放，避免重复文本或工具调用。并发限制与超时用于控制资源；高级权重、跨机器调度暂缓。

### 5.5 日志

日志定位为本机结构化排障工作台，一次根请求关联多次上游尝试，分别记录上游传输、Anchor 校验 / 转换、生成状态与客户端交付。记录实例、绑定、公开 / 实际模型、供应商、Key 标识、协议路径、配置版本、耗时、结构化错误及可获得的用量。

默认不记录完整对话、请求认证头或秘密；上游缺失用量标为未知，不伪造精确统计。请求明细与累计用量分开保存，清理日志不影响累计用量。首版计划包含请求日志、系统日志及 CLI / 桌面查询；管理审计后续增加。保留、容量、隐私、接口与页面基线见[日志设计](logging.md)（2026-10-11 定稿，尚未实现）。

## 6. 托管层与扩展契约

### 6.1 Binding

Binding 表示具体托管目标：适配器及版本、目标用户 / 配置 / Profile、启用选择、客户端协议、模型策略、网关绑定与凭据引用、revision、修改记录和状态。

产品名称不等于唯一目标。同一 Agent 可有多个非重叠配置目标，但不得同时由两个 binding 管理同一字段。

### 6.2 GatewayBinding

代理给托管层提供类型化连接信息：绑定 ID、协议对应地址、公开模型目录、默认模型、能力、配置版本及绑定级网关凭据引用。

不同 Agent 可能自行追加不同路径，适配器按真实客户端验证，不统一硬拼 `/v1`。地址来自目标实例，不来自控制电脑。

### 6.3 内置与声明式适配器

内置适配器用于 Codex、CC、DSH 的版本、配置层级、模型目录和认证差异，提供 Discover / Inspect / Plan / Verify 等契约。

声明式适配器用受限的 JSON / YAML / TOML 字段操作，将网关地址、网关凭据和模型映射到用户批准的配置文件。只支持白名单数据与字段操作，不执行脚本或任意表达式。

支持非主流 Agent 必须同时满足：

1. 它允许配置 API 连接。
2. 其协议与所需能力已经被代理支持。

导入描述不能自动解决未知网络协议。对只能通过启动环境 / 参数接入的 Agent，应明确 manual / launch-scoped 状态；不偷偷替换原二进制、alias 或全局 PATH。

### 6.4 状态与证据

分别报告：用户已选择托管、配置已应用、有效配置是否被覆盖、是否冲突、是否需重载 / 重启、是否观察到真实代理请求。

文件写入成功不等于实际链路已验证。没有请求就不能显示实际代理验证通过。默认不为了验证而自动启动带任务权限的 Agent。

## 7. 生命周期与配置恢复

### 7.1 用户选择

选择托管是持久策略，当前已接管是运行状态。正常停服并恢复配置后，下次启动仍根据启用策略自动接管。

新增托管对象必须显式选择；不因扫描到安装或导入描述就自动接管。

### 7.2 启动

取得实例锁 -> 核对未完成记录 -> 启动代理并确认就绪 -> 为启用 binding 生成 / 校验计划 -> 持久记录原值与恢复材料 -> 应用配置 -> 发布逐 binding 状态。

代理初始化失败不修改 Agent 配置。某 binding 失败不强行覆盖，其他已就绪 binding 可继续服务，但必须报告部分失败。

重启沿用并核对已有恢复记录，不能把上一次 Anchor 写入的配置重新认作原配置。

### 7.3 正常停止与取消托管

真正停服时冻结新配置修改，对托管字段条件恢复，处理已接受请求并有限等待后关闭代理。已有 Agent 会话可能仍使用旧连接，必须提示按适配器要求重新加载 / 重启，不承诺无缝迁移。

取消一个 binding 仅恢复它的字段，不停止代理或影响其他 binding。管理 CLI / SSH / 未来桌面窗口退出不触发恢复。

### 7.4 字段级条件恢复

| 停止时观察值 | 处理 |
| --- | --- |
| 等于 Anchor 写入值 | 恢复原值，包括原先不存在的状态 |
| 已等于原值 | 视为已恢复 |
| 为第三个值 | 保留并报告冲突 |

备份用于兜底，不无条件整文件覆盖。恢复材料可能含原有秘密，必须按目标用户权限保护。仅清理确认属于本 binding 且未被用户改动 / 引用的工件。

运行中不不断强制改回代理地址；用户变更应产生 overridden / conflict 状态。

### 7.5 异常退出与一致性

强杀、断电和系统故障不承诺即时恢复。首版采用持久恢复日志、启动核对和独立本机恢复命令，不增加第二个常驻看门狗。

配置 revision、操作 ID 和幂等性保护远程变更；写请求断线后应查询结果，不能盲目重放。多文件、数据库与配置文件不天然原子，必须记录分步进度和可恢复状态。

路径锁只能协调 Anchor，自身不能阻止所有外部编辑器竞争；发布前重检文件状态，发现变化则拒绝过期计划。

## 8. Context 与跨 SSH 管理

Context 是控制端本地连接档案：名称、连接方式、地址 / SSH 别名、预期实例 ID 和管理凭据引用，不保存远端业务配置副本。

- 本机通过回环管理 API；远端首版通过系统 OpenSSH 隧道。
- 远端需预先安装并运行 Anchor，具备 SSH 登录和转发权限。
- 首次连接校验 SSH 主机身份，取得独立管理授权，确认 Anchor 实例后绑定。
- 普通 CLI 命令按需创建并回收隧道，持续日志命令在其生命周期内保留连接。
- 不关闭用户已有 SSH 会话，只管理本次创建的进程 / 文件。
- 切换默认 Context 只改变管理目标，不改变任何模型流量。
- 不可达时明确失败，不回退到本机或其他设备。
- 远程修改要求显式目标及确认；操作目标在命令开始时固定。
- 核心未运行时，远端恢复需在目标机器本机 / SSH 登录执行，不能通过不存在的管理服务完成。

实例 ID 不等于 hostname：Windows、WSL、不同用户或容器可以各有实例。实例 ID 用于防误连，不代替 SSH 身份校验与认证。

## 9. 安全与无头运行

模型面与管理面默认分别监听本机回环地址，使用不同凭据与权限。专题中 `17860` / `17861` 只是候选端口，可配置，尚未冻结。

| 秘密 | 归属与边界 |
| --- | --- |
| 供应商密钥 | 目标实例保存，Agent / 普通管理输出不可获得 |
| 网关凭据 | 提供给托管 Agent，仅允许模型调用 |
| 管理令牌 | 控制端保存，独立授权、可撤销，不提供给 Agent |
| SSH 私钥 | 复用用户原有 SSH 环境，不复制导入 Anchor |

其他要求：

- 不因 loopback / SSH 转发而免认证，不默认开放公网管理或任意 CORS。
- 默认以目标用户身份运行，只操作批准路径；校验符号链接及平台路径边界。
- 秘密不进入普通 Context 文件、命令行参数、计划预览和日志。
- 无头凭据读取不能要求图形钥匙串解锁或弹窗；存储方案要验证 Linux / Windows 无头场景。
- 受限文件权限不等于静态加密，不宣称已经实现尚未验证的凭据保护。
- 不自动提权、安装远端服务或修改 SSH / 防火墙配置。
- CLI 机器输出保持结构化；JSON 数据写 stdout，诊断写 stderr。

服务可由前台 `serve` 或后续服务管理方式运行。常驻指核心独立于管理客户端；关闭承载前台服务的终端可能停止该服务。自动服务注册 / 自启动不在本轮假定已实现。

## 10. CLI 与未来桌面端

拟定使用流程：

```text
anchor init
anchor serve

anchor context add local --local
anchor context add dev-a --ssh dev-a
anchor context use dev-a
anchor --context dev-a status

anchor --context dev-a provider add
anchor --context dev-a model add
anchor --context dev-a agent manage codex --preview
anchor --context dev-a agent manage codex
anchor --context dev-a log follow
```

核心停服或尚未启动时的本机恢复入口拟定为 `anchor recover`。具体子命令、退出码和 API 字段见专题，仍待实施定稿。

CLI 与桌面端共用类型化业务 API 和连接组件。未来桌面可保持长期 Session、显示设备下拉框并隔离不同实例缓存，不通过解析 CLI 表格输出实现业务。Windows / Linux 正式桌面版均须双击打开 GUI，由宿主安全初始化缺失状态、自动启动或核验复用本机核心，不要求用户手动运行 CLI。桌面退出不隐式停止核心；显式停服是单独确认操作，开机自启动是默认关闭的独立选择。共同产品行为见[前端规范 §1.1](frontend.md#11-已确认的桌面启动与生命周期目标2026-10-11)，本机开发宿主与独立核心协调已实现，见[桌面运行契约](desktop-runtime.md)；安装入口、自启动设置与双平台原生验收未完成。

## 11. 实施顺序建议

以下是用于后续分任务的顺序，不是已完成进度：

1. **核心与连接骨架**：无头运行、监听与认证、本机 status、SSH Context、隧道清理。
2. **代理最小闭环**：供应商、模型映射、Responses 客户端与上游、基础流式 / 工具调用。
