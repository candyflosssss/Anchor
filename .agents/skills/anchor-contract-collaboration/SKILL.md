# Anchor 多 agent 契约协作

## 原则与适用边界

**前后端 agent 必须基于同一版本契约开发；不得自行推测、单方面修改或以 Mock 通过代替真实接口验收。**

- 聊天用于协调，仓库中的类型、语义契约、共享样例及其版本才是实现依据；任务记录不替代当前契约。
- 前端职责与 MVC 读取 `.agents/skills/anchor-frontend-architecture/SKILL.md` 和 `docs/design/frontend.md`；用户可操作功能同时遵循 `.agents/skills/anchor-cli-docs/SKILL.md`。
- 先核对 `internal/client/client.go`、相关 core/state/managed 实现和 `docs/design/implementation.md`，再约定接口。不假定计划中的桥接、类型生成器、Mock 或契约测试已经存在。
- 本 skill 规定已授权并行任务的协作方式；不把“咨询怎么分工”或“编辑规则”当作实施授权，不自行创建用户聊天、发布版本、提交推送或修改真实运行配置。

## 1. 主 agent 先建立最小共同基线

每轮围绕一个可交付功能切片，如供应商列表与编辑，不先设计全产品接口。

1. 检查工作区与现有改动，区分当前任务和历史未提交内容；不得覆盖、撤销或自动提交无关改动。
2. 主 agent 先解决阻塞双方的契约问题，明确当前立即要做的本地工作，再分派可独立并行的实现；不要把关键阻塞交出去后空等。
3. 为本轮记录契约标识、基线提交（已有时）、规范源 / 语义文档 / 样例的具体路径与版本。未提交契约可用内容摘要与明确快照标识，不为获得提交号擅自提交。
4. 把相同基线交给双方。独立 worktree / fork 不能假定看得到主工作区未提交文件；通过工具支持的补丁或文件同步交付，并确认双方收到的版本一致。
5. 分派前明确本轮交付、允许写入的文件、禁止修改的共享文件、测试及验收条件。契约关键项未定时，不启动依赖这些项的实现；可先做不受影响的页面骨架或内部逻辑。

## 2. 分工与共享文件归属

| 角色 | 默认负责 | 边界 |
| --- | --- | --- |
| 主 agent / 集成负责人 | 契约定稿、共享文件协调、变更决策、集成和最终验收 | 审核实际差异与测试，不仅接收“已完成” |
| 后端 agent | Go 核心、客户端、Wails 薄桥接及相应测试 | 不私改已约定的数据或行为，不复制前端交互逻辑 |
| 前端 agent | 前端功能模块 MVC、桌面传输适配器、Mock 消费与前端测试 | 不猜接口、不绕过后端权限、不直接修改核心 |

- 默认一个前端、一个后端执行角色；需要更多 agent 时再按独立功能和不相交写入范围拆分，不强制凑人数。
- 契约源、共享样例、生成文件、依赖清单 / 锁文件、跨层公共文档逐项指定唯一写入负责人，默认为主 agent；可明确交给某个执行者，但不能双写。后端可提交 Go DTO 变更提案，不擅自合入共享规范源。
- 契约类型优先与业务实现分文件，减少共享文件冲突。不同 worktree 仍须限制写入范围；它们只隔离编辑，不消除合并冲突。
- 给执行者的任务必须包含直接实现、具体文件范围和交付要求；主 agent 同时做非重叠的集成准备，不重做已委派工作。只有下一步确实依赖结果时才等待，结束后释放不再需要的 agent。
- 并行编辑不等于并行重构建：主 agent 协调重任务串行，通过 `resource-guard` 运行；各 agent 不能各自开一个重型测试把机器占满。

## 3. 契约的三个组成部分

### A. 机器可检查的结构：一个规范源

前端依赖明确的桌面接口 DTO，不直接绑定数据库对象或任意 `map[string]any`；HTTP 管理契约与桌面契约分清层次，由桥接负责明确转换。

- 对 Anchor 优先评估 Go 桌面 DTO / 绑定生成 TypeScript 类型，搭建时验证字段与错误的实际序列化结果。只有选定并验证的生成入口才写为可用流程。
- 每个接口层只有一个规范源；若选择独立 schema，则 Go / TS 从该源生成或校验，不再把手写 Go 类型当第二份权威定义。不要同时手写 schema、Go、TS 三套独立契约。
- 固定字段名、可选 / 可空、枚举、列表空值、时间格式 / 单位、数字范围以及缺省值；特别核对 Go 零值 / omitempty 与 TS undefined / null 的对应关系和大整数精度。
- 生成文件不手改，约定生成命令、工具版本及生成结果的提交策略。测试检查类型可重生成且消费者能通过类型检查；暂未具备生成器时明确过渡期校验方式，不宣称已自动同步。

### B. 语义文档：记录类型不能表达的行为

真实接入前，在 `docs/design/` 建立或更新对接契约，并从 `docs/design/frontend.md` 链接。文档注明草案 / 已批准 / 已实现 / 已验证范围，不用一份未验证设计冒充运行行为。

每个操作明确：

- 方法、只读或写入、输入 / 输出、创建与更新、完整替换或局部更新、缺省 / null / 空字符串的区别。
- revision / fingerprint 的来源和冲突处理；不自动覆盖，不将一次只读检查当作写入安全保证。
- 错误码及分类、可展示的脱敏信息、是否可重试；禁止前端解析任意错误文案。取消或超时不等于回滚，写入结果未知不得盲目重试；需要幂等时明确后端实际机制。
- 管理鉴权与实例身份边界，切换实例后的请求取消 / 旧结果丢弃 / 缓存隔离规则。
- 密钥只入不出、保留 / 替换 / 清除是否支持、日志脱敏、能力缺失时的 UI 行为；实例就绪、保存成功、上游连通分别表达。
- 涉及时才定义窗口与核心生命周期、进程归属，以及事件订阅、顺序和清理，不为不存在的事件流造接口。

### C. 共享样例：双方用同一批数据验证

- 样例只用合成数据和测试凭据，集中维护；前端 Mock 与后端契约测试读取同一份样例或从同一规范源生成，不各编一套。
- 按功能覆盖成功、空列表、非法输入、版本冲突、实例不可用、未授权和写入结果未知；注明样例属于哪个接口层，HTTP 与桌面格式不同时验证桥接映射。
- 类型检查只保证结构的一部分；测试还应检查序列化、错误分类、revision、秘密不回显等实际语义。Mock 通过只能证明前端对约定场景的处理。

## 4. 接口变更协议

执行者发现契约缺口时，发送以下内容给主 agent，不私自加字段或宽松兜底：

```text
当前契约标识：
涉及方法 / 字段：
现有行为与期望差异：
变更原因与证据：
兼容性及对另一方的影响：
建议的类型 / 文档 / 样例 / 测试调整：
受阻范围与可继续工作：
```

主 agent 核对实现与消费者后决定；产品或授权范围不明确时询问用户。批准后先更新规范源、语义和样例，分配新标识，再同步双方；双方确认基线后继续受影响的实现。不能让一方按旧契约、另一方按新契约交付。

不要默认“只增加字段就兼容”：检查严格 JSON 解码、未知枚举、旧客户端与响应形状。破坏性变更须说明迁移 / 同步发布范围；不得顺手改变既有 CLI 输出。拒绝或暂缓的提案不留隐式兜底实现；等待期间只推进不受影响部分。

## 5. 交接与集成门槛

每个执行者交付：

```text
基线及契约标识：
完成的功能 / 方法：
修改文件与可应用的补丁或提交标识（仅在已获提交授权时）：
实际测试命令、结果及所在环境：
Mock 覆盖与真实接口验证分别是什么：
未实现 / 未验证 / 已知风险：
需要另一方或主 agent 处理的事项：
```

主 agent 集成时：

1. 检查改动归属和实际 diff，保留无关工作；确认双方契约版本一致，无生成文件手改或第二套手写类型漂移。
2. 合入后重新运行相关生成 / 漂移检查、类型检查、前后端测试与桥接映射测试；不能只引用合并前各自工作区的通过结果。
3. 使用隔离状态和模拟上游，验证真实桌面调用链，包含至少一条读操作、一条涉及本轮功能的写操作和对应错误 / 冲突处理；纯只读切片不为凑测试执行写入。禁止改用户真实 Agent 配置或请求真实付费上游。
4. 按 `docs/design/frontend.md` 记录目标平台实际验收。未运行某平台或真实桥接时标为未验证，不以 Mock、Chrome 或编译通过代替桌面验收。
5. 同步当前规范、CLI 覆盖与必要的用户说明。同一协作任务由主 agent 汇总生成一份 `record-task-update` 记录，执行者回传证据不重复写记录；独立任务或实际打包发布仍遵循其对应记录要求。

只创建或修改本 skill 时，做格式、引用和规则一致性检查即可；不为验证流程搭建空前端、生成虚假契约产物或启动并行开发。
