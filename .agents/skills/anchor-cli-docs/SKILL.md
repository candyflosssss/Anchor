# Anchor CLI 文档与功能覆盖

## 权威入口

以仓库根目录为基准：

- `docs/cli/commands.md`：唯一最新指令大全，只描述当前实现。
- `docs/cli/changes.md`：追加式指令变更历史，不用它判断当前支持情况。
- `internal/cli/cli.go`、`cmd/anchor/main.go`：当前路由、参数、帮助和退出行为；涉及语义时同时核对 state/client/core 实现与测试。
- `docs/design/implementation.md`：安全、协议与实施范围；设计文档中的计划不是已实现指令。
- `docs/updates/`：每任务具体改动与实际验证结果，不代替指令变更历史。

README、设计说明和示例应链接到指令大全，不再维护另一份完整目录。出现冲突时先核对实现，修正文档，不通过虚构命令填补计划。

## 开发时的约束

大部分用户可操作功能应有 CLI。新增配置、查询、连接、绑定、恢复、授权等操作时，优先沿现有类型化客户端补命令；只有 API 或 UI 不算通常意义上的完整管理功能。

内部算法、后台机制、协议数据面和纯展示功能不必各造一个命令。暂未提供 CLI 的用户操作，要在指令大全的功能覆盖表中写明原因、替代方式或后续缺口，不把未实现命令放进可用目录。CLI 入口不得绕过核心鉴权、实例校验和配置写入边界。

任何以下变化都需要同步文档和历史：

- 命令或别名新增、删除、重命名、废弃。
- 参数新增、移除、改名，必填性、类型、范围或默认值变化。
- Context/本机作用域、前置条件、副作用、输出结构、退出码变化。
- 密钥输入输出、重试、幂等性、恢复或兼容边界变化。

纯内部重构且对外行为不变时，不制造虚假的指令变更记录。

## 每轮完成标准

1. 对照实现和现有大全核对受影响命令及功能覆盖；开发功能时同时评估 CLI 入口。
2. 同一轮更新实现、帮助、相关测试和 `docs/cli/commands.md`。每个命令至少说明用途、完整语法、参数/默认值、前置条件、作用域、输出、副作用和重要失败情况；共享语义可集中描述并引用。
3. 更新大全的核对日期/适用版本；删除的命令从当前目录移除，必要的迁移说明放入历史，不继续作为可用命令展示。
4. 在 `docs/cli/changes.md` 追加一条本轮实际契约变化记录，注明日期、适用版本/未发布状态、变更类型、旧→新行为、兼容影响、迁移方法和实际验证。不能提前写入未来变更，不改写旧记录，不记录真实秘密。
5. 按风险验证帮助、受影响命令的成功/失败路径、输出和作用域；写操作使用隔离状态和模拟上游。重型测试/服务通过项目 resource-guard 规则执行。只修改文档时核对源码、链接和 skill 元数据，不必调用真实服务。
6. 按项目记录规则生成恰好一份任务更新记录；最终报告指令变化、文档入口、CLI 缺口和实际验证。不得把“文档已更新”写成“功能测试已通过”。

变更历史的一条记录可覆盖多个命令，格式保持：

```markdown
## YYYY-MM-DD — 简短标题（适用版本或未发布）
- 类型：新增 / 删除 / 修改 / 重命名 / 废弃 / 基线收录。
- 指令与参数：具体受影响入口。
- 旧 → 新：实际差异；基线收录说明仅登记既有实现。
- 兼容与迁移：是否破坏兼容；破坏性变化写出替代方式，无替代则明确说明。
- 验证：实际执行结果或未执行的理由。
```

示例只使用占位密钥或 stdin；不要把令牌放到命令参数、历史、更新记录或日志中。不要为了检查文档读取现有 Agent 配置或调用付费供应商。
