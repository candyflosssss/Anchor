# Anchor 前后端分离与前端 MVC

## 开始工作

以下路径均相对仓库根目录。先确认本次是设计、原型还是真实功能接入，不把计划当作已实现能力。

- 前端任务先读 `docs/design/frontend.md`：这是技术、视觉、组件、交互、MVC 与跨平台要求的权威入口。修改哪部分，就核对对应章节；不要只看本 skill 的摘要。
- 桌面真实接入读取 `docs/design/desktop-runtime.md` 与 `docs/design/provider-interface.md`；`internal/desktop/contract.go` 是桌面 DTO 规范源，用 `go run ./cmd/desktop-contract` 生成 TS，禁止手改生成文件；Go 漂移测试与前后端共享样例须一起更新。
- `prototype` 仅供明确标注的内存预览；`desktop` 只能走受控桥接，缺绑定、授权或连接时必须报错，不能回退 Mock。浏览器模拟绑定、隔离 Go 核心测试与两平台原生窗口验收分别记录。
- 真实接入或接口变更时，按需读 `docs/design/implementation.md`、`internal/client/client.go` 及对应 core/state/managed 实现；Agent 接管另核对 `docs/design/agent-management-layer.md`。先查现有能力，再设计接口，不猜测 API。
- 涉及用户可操作功能时，同时遵循 `.agents/skills/anchor-cli-docs/SKILL.md`；外观偏好等纯展示不必硬造 CLI。
- 前后端由多个 agent 并行实现或涉及共享契约变更时，同时遵循 `.agents/skills/anchor-contract-collaboration/SKILL.md`；本 skill 定义分层，该 skill 定义共同基线、文件归属、变更协商与联调验收。
- 本 skill 固定职责边界，不授权另建 Web 产品、更换技术栈、重构整个核心、发布或修改用户真实配置。

## 前后端边界

- **前端**负责展示、表单草稿、交互流程和反馈；**Go 宿主 / 连接层**负责受控桌面能力与连接；**核心**负责业务校验、授权、持久化、代理、Agent 文件修改和恢复。
- 默认接入方向：前端 Model → 类型化桌面接口 → Wails Go 薄适配层 → 现有 `internal/client` → 管理 API。CLI 与 GUI 共享核心规则，不通过拼接 CLI 命令或解析终端文本实现页面功能。
- 页面和前端 Controller 不直接调用 Wails 生成绑定；集中在 Model 使用的传输适配器后面。简单功能可合并 Model 与适配器文件，不要求一函数一接口。
- Wails 适配层不是前端 MVC 的 Controller，也不成为另一套业务后端；只暴露明确、受限的方法，不提供任意 shell、SQL、文件读写或任意目标 URL 请求入口。
- UI 不直接访问 SQLite、不直接修改 Agent 配置、不实现 SSH / 隧道 / 上游代理。不得为了接页面删除现有 Origin 防护、启用任意 CORS 或绕过实例身份校验。
- 实例和连接策略在 Go 侧处理；切换实例后丢弃旧查询结果并隔离缓存，防止把旧实例数据或表单误提交到新实例。
- 前端不持久保存管理令牌或供应商 API Key，不将秘密放入日志、URL、剪贴板默认操作或错误详情。供应商密钥只在必要表单内短暂输入和提交，成功、取消或卸载时清空；失败重试的暂存范围要明确。编辑时区分保留、替换和清除；按已核对的核心能力决定是否可用。当前供应商支持 null 保留、非空替换、空字符串清除；清除须明确确认，不能用掩码作为实际密钥回传。
- Windows 与 Linux 均须满足 `frontend.md` §1.1：用户双击直接打开 GUI，Go 宿主安全初始化缺失状态并自动启动／核验复用本机核心，不要求手动终端；开发宿主、Mock 与已公开的 CLI 包不代表已完成两端安装验收。
- 核心与窗口生命周期分离。关闭窗口／退出界面不隐式停服，后台核心须能在宿主退出后继续工作；区分宿主创建与既有实例，并发启动遵循实例锁，身份不符或端口冲突不得强杀或覆盖。
- 显式停服必须确认目标与影响，复用核心正常停服和托管条件恢复；非自建进程不自动接管停止方式。开机自启动为独立、默认关闭的用户选择，安装不自动提权／注册系统服务。宿主与双平台原生验收前不得宣称双击即用已实现。

## 前端内部 MVC

MVC **仅约束前端**，不要求核心改造成 MVC，也不以架构名称或评分替代验证。

| 层 | 职责 | 禁止混入 |
| --- | --- | --- |
| Model | 前端业务类型、数据访问、转换、服务端状态的统一来源 | React 展示、系统操作、后端权限与路由规则 |
| View | 页面、表格、表单控件、状态与错误展示；轻量局部视觉状态 | 直接请求后端、业务提交流程、秘密持久化 |
| Controller | 以自定义 hook 协调加载、表单提交、确认、刷新与错误处理 | JSX 布局、传输实现、数据库或文件操作 |

- 按 `features/<业务功能>/` 组织 Model、Controller、View，而不是全局三个大目录。`pages/` 作为装配入口，基础组件与公共外观组件保持可复用。
- Controller 优先用 `use…Controller` hook；不用强制 class、不为每个按钮建控制器，也不让一个 hook 管理整个应用。
- 同一服务端实体只有一个权威数据来源；表单草稿与已保存数据分开，区分加载、提交和结果状态。组件可保留弹窗开关等局部状态，不把所有状态提升为全局状态。
- 前端校验服务于即时反馈，核心仍做最终判断。更新携带当前 revision；冲突提示重新读取或比较，不静默覆盖。结果未知的写请求不盲目重试。
- 有副作用的操作先显示目标与影响；Agent 接管保留计划审核、明确确认、fingerprint / revision 校验及恢复反馈，不用“保存成功”冒充已接管或已连通。

## 融合现有前端规范

不在 skill 复制完整颜色表、尺寸表或平台依赖列表；使用 `docs/design/frontend.md` 对应章节：

- **§2 技术选型**：React、严格 TypeScript、shadcn/ui、Tailwind、Vite、Wails；初始化时核对并锁定兼容版本与依赖锁文件，不在普通功能任务顺手升级整套框架。
- **§3–5 视觉与交互**：克制的管理工作台、统一语义主题、浅色 / 深色 / 跟随系统、可见标签、风险确认、键盘焦点和中文输入法；保留错误和未保存提示，不以 toast 代替重要信息。
- **§4、§5、§8 状态真实性**：覆盖加载、空数据、正常、错误、离线、未实现及结果未知；模拟数据明确标注，配置成功不等于上游已验证。没有对应后端能力时不展示假可用按钮。
- **§6 工程组织**：功能模块 MVC、公共组件分层、文案集中管理、离线静态资源；不在前端目录之外随意散落界面代码。
- **§7–8 双平台验收**：Linux / Windows 真实 WebView、中文输入、键盘、小窗口、长文本、缩放与主题；不能用 Chrome 预览替代双平台验收。日志和列表的保留量须受限。

## 官方 Blocks 视觉基线

- 用户已指定 `https://ui.shadcn.com/blocks` 为视觉与布局基准；先核对 `frontend.md` §3–4 和功能设计文档，再修改界面。首个供应商切片选定 `sidebar-07` 的可折叠侧栏与 inset 内容骨架。
- 读取实际官方 Block / 组件源码后按需引入，记录上游地址、版本 / 内容标识、许可和适配差异。当前 Tailwind v3 / Radix 可使用官方 v3 同名源码，不直接混用 Tailwind v4 / Base UI 实现。
- 桌面窗口遵循 `frontend.md` §4.1：Windows / Linux 去掉原生系统标题栏，将拖动区和窗口按钮融入现有 header；不因只改网页内容而保留突兀的系统标题栏。窗口控制必须经过受限 runtime 适配器与前端 Controller，按钮排除拖动，关闭 GUI 不等于停核心；原型不展示假可用窗口按钮，未做原生验证就明确记录。
- 保留官方结构、neutral 黑白主操作和组件状态；只按业务需要改文案、数据、功能槽位、无障碍与语义状态色。不得把自绘侧栏、其他品牌风格或仅换色的旧布局称为 Blocks 实现。
- 不因示例含图表、团队、账户或项目就增加虚假功能。Mock 和未接入标识必须保留。
- 视觉方向变更时先同步权威设计文档和本 skill，再改 UI。验收时对照选定 Block 的结构、浅 / 深主题、折叠与移动行为及实际截图；仅安装 shadcn 依赖不算风格验收。

## 接口与文档同步

真实接入前，在 `docs/design/` 的对接文档明确契约并从 `frontend.md` 链接；复用已存在的文档，不为每个按钮建立新文档。至少记录：

- 调用方法、输入 / 输出类型、字段可空性、创建 / 更新语义和 revision；秘密保留 / 替换规则。
- 实例选择、认证边界、错误分类、超时 / 取消、写入结果未知、重试约束。
- 能力缺失时的展示、进程归属和窗口 / 核心生命周期；有事件时再定义订阅与清理。

按改动范围同步，不机械触碰无关文件：

| 改动 | 必须核对或同步 |
| --- | --- |
| MVC 边界、技术栈、组件规范、页面交互或平台基线 | `docs/design/frontend.md` 相应章节；规则改变时同步本 skill |
| 桌面桥接、管理 API 或状态语义 | 对接契约、相关类型与测试；后端实现范围变化时更新 `implementation.md` |
| 用户管理功能 / 实际 CLI 契约 | 按 `anchor-cli-docs` 更新覆盖表；有实际命令变化才改帮助、最新大全和 CLI 变更历史 |
| 用户启动、安装或使用方式变化 | README 与对应使用 / 发行文档；设计能力不得写成现成命令 |

设计结论、实现状态、实际验证分开写；更新已有结论，不保留相互矛盾的“完全待定”和“已确定”。任务记录不能代替当前规范。

## 完成前检查

- 检查依赖方向：View → Controller → Model → 传输适配器；无前端越界、无 Go 侧重复业务规则，纯视觉状态不强制过层。
- 按范围验证 Model 数据转换 / 请求语义、Controller 成功 / 失败 / 冲突 / 重复点击、View 状态 / 焦点 / 中文输入，以及类型检查 / lint；工具链尚未建立时明确说明，不虚报通过。
- 接入测试使用隔离状态、模拟上游和测试凭据，不修改真实 Agent 配置或请求付费上游。浏览器 / 桌面集成和重构建遵守 `resource-guard`，缺少某平台验收就明确记录未验证。
- 纯 skill / 文档任务做格式、引用、规则一致性检查即可，不为验证文档启动服务或构建前端。
- 持久改动完成后按 `record-task-update` 生成恰好一份当前任务记录；记录实际执行的验证、未覆盖范围和涉及文件。
